# Logging spec — seeing what's wrong, fast

Status: implemented 2026-08-04 (engine ring + `GET /log`, `core/log.js`, F9 debug
panel, request-id correlation). Owner: Claude.

The logs feed the golden-matrix QA loop (`tools/qa/`, workflow `qa-matrix`):
explicit input cfg → expected output per cell, invariants judged numerically
against engine `/state` rects, failing cells reviewed by agents from artifacts
alone. Central telemetry was considered and rejected — no user scale to justify
it; the QA loop on the owner's machines replaces it.

## Problem

When the editor misbehaves there is currently almost nothing to look at: the engine
bridge (`engine/src/hud_web.c`) prints nothing, and the UI has seven scattered
`console.error/warn` calls. Diagnosing "elements don't move", "editor won't connect"
or "rect is wrong" today means adding printfs and rebuilding. The goal: any failure
in the engine↔UI loop should be explainable from logs the user (a non-developer
player) can copy-paste, without a rebuild and without a toolchain.

## Principles

- **Two sides, one story.** Every bridge request gets a short request id generated by
  the UI and echoed by the engine, so a UI log line and an engine log line about the
  same request can be matched.
- **Off by default, cheap when off.** The engine is a game; logging must never cost a
  frame. Everything is gated and ring-buffered, never written synchronously to disk.
- **Copy-pasteable.** The unit of support is "paste me your log". Both sides must be
  able to dump their buffer as plain text in one action.
- **`core/` stays DOM-free.** The UI logger lives in `core/`, sinks (console,
  on-screen panel) live in `view/`.

## 1. Engine side (C, `hud_web.c`)

New cvar `hud_web_log` (default `0`):

| value | logs |
|---|---|
| 0 | errors only (bind failure, token rejection count, client drop) |
| 1 | + one line per request: method, path (token redacted), status, bytes, ms |
| 2 | + command traffic: every console command the bridge executes on behalf of the UI, and every cvar it reads/writes |

- Sink: in-memory ring buffer (256 lines) + `Con_Printf` prefixed `[hud_web]` when
  `hud_web_log >= 1`. Errors always go to the console.
- **Never log the token.** Redact `?t=` in every line.
- New endpoint `GET /log` (token-gated): returns the ring buffer as `text/plain`.
  This lets the UI show engine-side history even for events that happened before the
  page connected.

## 2. UI side (JS)

New module `core/log.js`:

- `log(level, area, message, data?)` with levels `error|warn|info|debug` and areas
  matching the module map: `bridge`, `model`, `geometry`, `view`, `fte`, `import`.
- Ring buffer of 500 entries, each `{t, level, area, msg, data, reqId?}`.
- Sinks are pluggable; `view/` registers the console sink. `debug` is enabled via
  `?debug=1` or `localStorage.ezhud_debug` — no rebuild, per Principles.
- Replace the existing ad-hoc `console.*` calls in `view/app.js`, `core/bridge.js`,
  `fte/boot.js` with it.

What must be logged:

- **bridge**: every request at `debug` (path, reqId, ms, status); every `BridgeError`
  at `error` with status and whether it is the fatal 403; reconnect/poll transitions
  ("lost contact" ↔ "reconnected") at `info` — flapping here is the #1 suspected
  failure mode.
- **model**: every mutation applied (element, cvar, old→new) at `info`. This is the
  audit trail for "my cfg changed and I don't know why".
- **geometry**: any `rect: null` element the user tries to interact with, and any
  physical/console scale fallback, at `warn` — the protocol doc calls these out as
  silent-wrong-layout traps.
- **fte/boot**: Emscripten `print/printErr` routed through the logger under area
  `fte` instead of raw `console.log`, so engine spam is filterable.

## 3. Surfacing to the user

- A **debug panel** in `view/` (toggle key, off by default): merged view of the UI
  buffer and `GET /log`, filterable by level/area, with a **Copy log** button that
  produces one plain-text blob containing: UI log, engine log, protocol version,
  engine string, screen/physical dims, and the current element list summary.
- On any `error`-level event the existing error toast gains a "copy details" action
  backed by the same blob.

## 4. Tests & acceptance

- Tier-2 bridge tests assert `/log` exists, is token-gated, and redacts tokens.
- Tier-3/4 harnesses dump both buffers into the test artifact directory on failure,
  so CI failures come with the same blob a user would paste.

## Non-goals

- No log files written by the engine (crash-safe persistence is `Con_Printf`'s job).
- No remote/telemetry upload of any kind — the QA loop above is the deliberate
  alternative; do not reintroduce upload features.
- No new dependencies; `core/log.js` is a plain ES module like everything else.

## Cases

1. `hud_web_log 1` → each HTTP request produces exactly one `[hud_web]` console line
   with the token redacted.
2. `hud_web_log 0` → request lines are absent; a rejected token still logs an error.
3. `GET /log` without a valid token → 403; with token → last N lines, token-free.
4. UI `debug` disabled → no `debug`-level console output; `?debug=1` enables it
   without reload of the engine.
5. A model mutation logs old and new value with the element name and reqId, and the
   same reqId appears in the engine's request line at `hud_web_log 2`.
6. Killing the engine mid-session logs one `bridge` `error` ("Lost contact") and one
   `info` on reconnect — not one line per failed poll.
7. Copy-log blob contains both buffers plus protocol/engine/screen metadata.
8. Tier-4 failure artifacts include both log dumps.
