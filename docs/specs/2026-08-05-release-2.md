## 0. What the release must be true of, end to end

Placement stops being "drag, then nudge numbers". You pick what an element
hangs on, how it aligns, and the editor does the arithmetic — with snapping to
make dragging land on sensible values, an editor that fits the monitor you
actually use, and a demo you can park on the frame you actually want to edit
against. Every claim below is engine-observable, because the editor never
owns placement truth: the engine does.

Release-level acceptance lives in #62. This spec is the implementation contract.

## 2. #25 — editor window scaling

Two defects and one control:

- moving the browser between monitors (devicePixelRatio change) collapses the
  layout;
- the editor is too small to work in at 1440p;
- add a UI-scale control (presets or free) that persists across reload.

**Keep the concepts apart.** This is the *editor chrome* scale. The HUD's own
console-pixel scale model is #6 and is **not** in this release — do not
introduce a second control that could be mistaken for it, and do not reword the
existing `editing at … · 1 px = N×` readout.

**Regression watch:** this is the code Release 1's #40 fix landed in.
`tools/qa/assert_wasm_resize.mjs` and the matrix resize cells are the net;
both must stay green, and the canvas must still follow the window.

### Cases

1. A devicePixelRatio change (Playwright `deviceScaleFactor`, and a viewport
   change at fixed DPR) never reduces the editor below its usable layout —
   assert the stage and rail keep non-degenerate boxes and the canvas still
   fills its frame.
2. The UI-scale control visibly changes editor chrome metrics (measured
   element box, not a class name), and the choice survives a reload.
3. At a 1440p-class viewport the default layout is usable without manual
   scaling — assert against measured minimum sizes, not a screenshot.
4. `/state.screen` still follows the window after each scale change: the
   resize propagation assertion stays green.
5. Tier-4F row for the new control (#18 convention); case-35 coverage green.

## 3. #32 — alignment-first editing (the model)

Anchoring becomes the primary mechanism in the inspector: choose a parent
element or screen edge, an alignment and an order; `pos_x`/`pos_y` become
fine-tune offsets. Anchor relationships are visible on the stage so a drag
reads as "re-anchor plus offset" rather than raw coordinates. Raw coordinate
entry stays available.

The engine already exports `parent`, `place`, `align_x/y`, and `place`/`align`
are already allowlisted commands — this surfaces existing capability. Do not
invent a parallel placement model in the editor.

### Cases

1. Anchoring A to B: moving B moves A with it, proven by engine rect readback
   for both elements (not DOM geometry).
2. Changing alignment on an anchored element moves it to the expected edge or
   centre, verified by engine rect readback across at least three alignments.
3. A pos offset applied on top of an anchor lands as an offset from the anchor,
   not as an absolute coordinate.
4. The stage shows the anchor relationship for a selected element, and it
   updates when the anchor changes.
5. Raw coordinate entry still works and still reaches the engine.
6. **Handed over from #61.** At least one **left-aligned** tracker contract
   case exists, and the editor's overlay is verified to follow the *rendered*
   tracker rows — engine rect readback, not DOM geometry, and no mirroring
   arithmetic performed by the consumer. This is release acceptance criterion 2
   in #62; it is the only part of #61 that is release content.
7. A placement cycle (A anchored to B anchored to A) is refused with a stated
   reason rather than producing undrawable elements (see README known gaps).
8. Export round-trip stays byte-identical for untouched lines.
9. Every new control has its tier-4F row; case-35 coverage green.

## 4. #24 — snap grid + magnet alignment

Drag assistance on top of #32: snap-to-grid with a configurable step, magnet
alignment to other elements' edges and centres with visual guides, a visible
toggle, and a held modifier to bypass temporarily. **Editor-side only** — the
export contains final positions and nothing else.

### Cases

1. With snap on, several drags land engine `pos_x`/`pos_y` on multiples of the
   configured step (engine readback, not editor state).
2. With magnet on, dragging within threshold of another element's edge aligns
   the edges exactly (engine rect readback of both).
3. Toggling either off restores free-pixel dragging.
4. Changing the grid step changes what the engine values quantize to.
5. Holding the bypass modifier during a drag produces an unsnapped value.
6. The export gains no snap/magnet artefacts — round-trip unchanged.
7. Tier-4F rows for the new controls; case-35 coverage green.

## 5. #23 — preset demo moments (the remaining half)

Pause/Resume shipped in Release 1. The **preset jump points never did**: there
is no `demo_jump`, seek or preset anywhere in `hud_web_ui` on `main`, and
`demo_jump` is absent from the editor's command allowlist — only
`demo_setspeed` is there.

Add named preset moments that seek the demo to a deterministic point: a frame
with full HUD activity, a scoreboard moment, a quiet moment. Lining a HUD up
against a frame that has nothing on it is the same wasted work this release
exists to remove.

**Allowlist changes stay mirrored across both backends**, exactly the way
`demo_setspeed` is. An allowlist entry added on one side and not the other is a
defect, not a partial landing.

This ticket is also what gives the changedrop capture (§7) deterministic
starting states. Capture drift was measured at up to 0.815 s between runs, and
one Release 1 segment sat only 1.708 s under the 2.0 s dead-air limit.

### Cases

1. Each preset control seeks the demo to its point, proven by engine-state
   readback — not by an editor-side timestamp.
2. Two runs of the same preset land on the same engine state.
3. Placement edits made while paused still reach the engine **and** the export.
4. `demo_jump` (or whatever the seek command is named) is present in the
   allowlist on **both** backends; a test asserts the two allowlists agree.
5. Pause/Resume from Release 1 keeps working alongside the presets.
6. Tier-4F rows for the new controls; case-35 coverage green.

## 6. Release-note standard — required, not optional

This is user-visible work, so the standard merged in #57 applies in full:

- **Canonical document `docs/release-2/NOTES.md`**, in the shape the gate
  parses: title, one player-facing summary paragraph, `## Features` with a
  `### block` per feature carrying prose and exactly one
  `Evidence: img/<file>.png`, then `## Discord payload` with a fenced JSON
  block containing `content`, ordered `embeds` (title, description,
  `attachment://name` image), empty `allowed_mentions.parse`, and an
  `attachments` array mapping each name to its repo path.
- **The Release 2 ticket (#62) states that path** and carries its checklist.
- **Evidence with provenance**: focused captures declared in
  `docs/release-2/captures.json` and produced by `tools/release/capture.mjs`
  from an assembled dist; annotations declared in
  `docs/release-2/annotations.json` and rendered by
  `tools/release/annotate.mjs`. Sources are never hand-cropped or edited.
- **Focused crop, ring only the changed control**, small numeric badge, no
  magnified inset and no prose inside the image; behaviour is explained in the
  note beside it. At most 3:1 aspect, materially smaller than any full-frame
  context image. `docs/release-1/ANNOTATION-CONVENTION.md` is the worked
  example.
- **Non-image links wrapped in `<…>`**; no `/home/`, username or hostname
  anywhere in the note.
- The PR carries the `user-visible` label and names the canonical document, so
  `release-note-gate` applies and passes.

Reuse `docs/release-1` as the exemplar rather than inventing a second shape.

## 8. Testing and gates

Tier placement follows `docs/TESTING.md`. Engine-observable effects belong in
tier 4F as declarative rows; editor logic in tier 1/3F; geometry claims in the
QA matrix.

Per ticket: observe every new assertion **RED before implementing** and keep
the logs. Before reporting a ticket done, run `npm run test:tier1`,
`npm run test:tier3:fte`, `npm run test:qa`, a fresh
`BASE_PATH=/ezHUD/` assembly and `npm run test:tier4:fte` against it, plus the
QA matrix cells for anything geometric.

No ticket in this release touches the engine, so the tier-2 engine contract and
native tier 4 are not on any ticket's critical path. If a ticket turns out to
need an engine change, it stops being a Release 2 ticket until that is
re-approved.

**Daniel's QA is independent and comes after Bosse reports done** — never on
work he built himself, and never on a PASS carried over from a superseded
commit. Steve reviews the current head SHA before QA is asked for.
